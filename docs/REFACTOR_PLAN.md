## 1. Purpose and the key fact that shapes this plan

`coordinator.py` is **1164 lines** mixing five unrelated concerns. The goal is
to break it into focused, independently-testable modules.

**Unlike a from-scratch refactor, this project already has a complete test
suite — but that suite is structure-coupled, and that single fact drives the
entire plan.** Eight coordinator test files import private internals directly
(`_build_statistic_ids`, `_calculate_cost_for_wh`, `_aggregate_hourly_data`,
`_estimate_billing_cycles`, `_process_and_insert_statistics`, …). The file
names (`test_coordinator_chunk1/2/3`, `_coverage`, `_remaining`,
`_final_coverage`, `_complete`) show the suite was generated by iterating
toward a coverage number, not by specifying behavior.

Consequences, stated honestly:

- **Good:** the assertions exercise real logic, so they *do* catch behavior
  changes. This is a genuine safety net that a zero-test refactor lacks.
- **Bad:** because they import private functions by their current location,
  **every extraction will break their import lines** even when behavior is
  perfectly preserved. A green suite after a move is only meaningful if the
  breakage was "fix the import path," not "the test silently stopped testing
  the moved code."

So this plan treats the test suite as a **behavioral oracle to preserve**, not
as a structural contract to obey. The work is: move code, follow the import
breakage, and confirm the *same assertions* still run against the *same logic*
at its new location.

**Non-goals:** no behavior change in the pure-refactor phases; no change to any
statistic id for existing installs without an explicit migration (release-blocking).

### 2.4 Findings

- **F1 — Structure-coupled tests (the defining constraint).** See §1.
- **F2 — Pure helpers buried in the coordinator module.** Group B are pure
  functions mixed with HA-recorder I/O. Prime extraction candidates; already
  tested (via private imports).
- **F3 — Statistics machinery conflates fetch/aggregate/write.**
  `_process_and_insert_statistics` (~165 lines) fetches, filters, aggregates,
  costs, and writes in one method. Aggregation (pure) is entangled with I/O.
- **F4 — Uses the flat library API.** Calls `async_get_usage_reads` and
  destructures `async_get_accounts()` positionally. Does not yet use the new
  `async_get_register_reads()`; grid + solar-export are merged into one stat.
- **F5 — Statistic ids keyed per measurement type, not per register.**
  `_build_statistic_ids` yields one id per ELECTRIC/GAS. Per-register ids
  (grid vs solar-export) require care for existing installs (see Constraints).

## 3. Target structure

```
custom_components/dominionsc/
├── __init__.py            # unchanged
├── config_flow.py         # unchanged (tested, acceptable size)
├── const.py               # unchanged
├── sensor.py              # unchanged unless register entities need it
├── rates.py               # unchanged (already focused)
├── coordinator.py         # SLIMMED to lifecycle + orchestration
├── models.py              # NEW: the three dataclasses
├── billing.py             # NEW: billing-cycle estimation (pure, no HA)
├── cost.py                # NEW: cost calc + config resolution (pure, no HA)
├── statistics_ids.py      # NEW: statistic-id construction (pure, no HA)
└── statistics_writer.py   # NEW: aggregation + recorder insertion
```

Rules: `billing.py`, `cost.py`, `statistics_ids.py` import nothing from Home
Assistant. `statistics_writer.py` may touch the recorder, but its aggregation
logic should be a pure, separately-testable function. `coordinator.py` shrinks
to lifecycle + orchestration.

## 4. Phased execution

The test suite is the oracle. After every phase: `uv run pytest` must return to
**143 passed, 100% coverage**. The only permitted test edits during pure-refactor
phases are **import-path updates** — if an *assertion* has to change, stop and
understand why, because that means behavior moved.

### Phase 0 — Baseline + a compatibility shim decision

- [ ] Confirm `uv run pytest` = 143 passed, 100%.
- [ ] Decide the shim strategy up front: when a private function moves from
      `coordinator.py` to e.g. `cost.py`, re-import it back into `coordinator`
      (`from .cost import _calculate_cost_for_wh`) so existing test imports
      (`from ...coordinator import _calculate_cost_for_wh`) keep resolving.
      **This makes each extraction a two-line change instead of an 8-file
      test edit**, and keeps the diff behavior-preserving and reviewable.

**Acceptance:** baseline reproduced; shim approach agreed.

- [x] `models.py` ← the three dataclasses; re-exported from `coordinator`.

**Result:** 143 passed, 100%, **zero test edits**. `coordinator.py`
391 → 386 stmts. The re-export shim (`from .models import ...` + `__all__`)
meant the structure-coupled test imports resolved unchanged.

### Phase 2 — Extract pure cost/billing helpers — ✅ DONE

- [x] `billing.py` ← `_billing_cycle_get_gap`, `_estimate_billing_cycles`,
      `_find_billing_cycle_for_date`.
- [x] `cost.py` ← `_calculate_cost_for_wh`, `_resolve_cost_config`.

ruff auto-removed 13 now-unused imports.

### Phase 3 — Extract aggregation — ✅ DONE (SCOPED DOWN from the plan as written)

**The plan originally said:** extract all five stats methods
(`_push_cost_statistics`, `_backfill_statistics`, `_update_statistics`,
`_aggregate_hourly_data`, `_process_and_insert_statistics`) into a
`statistics_writer.py`.

**What was actually done, and why it deviates — disclosed, not glossed:**
Inspecting the real `self` coupling before moving anything showed the plan's
full-extraction target was **over-extraction**:

- `_push_cost_statistics` touches only `self.hass`; `_process_and_insert_statistics`
  touches `self.api`, `self.hass`, and two sibling methods;
  `_backfill`/`_update` are lookback/recorder-query logic bound to `self`.
  These are fundamentally *this coordinator's recorder-I/O*, not reusable pure
  logic.
- The tests **patch these methods on the coordinator instance**
  (`patch.object(coordinator, "_process_and_insert_statistics", ...)`) and call
  them as bound methods. Extracting them to a module of free functions, or to a
  delegating helper class, would add an indirection layer purely to satisfy the
  plan's file list — churn without payoff, and risk to the test contract.
- Only `_aggregate_hourly_data` had a genuinely pure core (one `self` touch:
  `self.config_entry.options`).

**So Phase 3 extracted only the pure aggregation:**

- [x] `aggregation.py` ← new pure function `aggregate_hourly_data(...)`, taking
      the resolved cost config (`cost_mode`, `fixed_rate`, `rate_schedule`,
      `is_tiered_rate`) as explicit parameters. No Home Assistant, no `self`.
- [x] `coordinator._aggregate_hourly_data` retained as a thin wrapper that
      resolves config from `self` and delegates, so tests calling or patching
      it are unaffected.
- [ ] ~~`statistics_writer.py` for the recorder-I/O methods~~ — **rejected as
      over-extraction.** The recorder methods stay on the coordinator, which is
      the correct home for *this integration's* recorder interaction. Revisit
      only if a second consumer of that logic ever appears.

**Result:** 143 passed, 100%, **zero test edits**. `aggregation.py` reaches
100% coverage through the *existing* tests alone — proof the extraction
preserved behavior exactly. `coordinator.py` 329 → 298 stmts.

> **Definition-of-done note:** the target "coordinator well under ~400 lines"
> is already met at 298 statements. The recorder-I/O methods remaining on the
> coordinator is a deliberate design choice, not unfinished work.

## 5. Constraints

**Statistic-id stability is release-blocking.** HA long-term statistics are
keyed by statistic id. If Phase 5 changes an existing install's id, the old
series is orphaned — the user's Energy Dashboard history silently detaches and
a new empty series begins. Before shipping Phase 5, choose one: keep the
existing per-measurement-type id as the primary/grid register and only *add*
ids for solar-export; provide an explicit statistics migration; or gate behind
an opt-in option. **A dedicated test must assert existing ids are unchanged.**

**`async_get_accounts()` is a cross-repo breaking change.** The coordinator
does `accounts, service_addr = await self.api.async_get_accounts()`. Migrating
the library to return `AccountInfo` requires changing this line and the library
together with a coordinated version bump.

**The test suite is a behavioral oracle, not a structural one.** Green after a
move only counts if the change was an import-path fix. If an assertion had to
change to stay green, behavior moved — investigate before proceeding.

**UsagePoint id stability is verified** (identical across exports months apart),
so it is safe as a durable statistic-id key.

## 6. Risks

| Risk | Mitigation |
|---|---|
| Extraction breaks 8 test files' imports | Re-export moved names from `coordinator` (Phase 0 shim) |
| A test silently stops testing moved code | Require diffs to be import-only; scrutinize any assertion change |
| `self`-dependent stats methods resist extraction | Pass `hass`/`config_entry`/options explicitly |
| Phase 5 orphans users' statistics history | Explicit id-stability decision + a regression test (Constraints) |
| Cross-repo `AccountInfo` change breaks setup | Coordinate library + coordinator + version bump together |
| Coverage-driven tests mask a real gap after refactor | Spot-check that key assertions are behavioral, not just line-touching |
